## 一、Type E 图片拖动边界修复

### 问题描述

Type E 样式中，顶部 1:1 正方形图片区域支持拖动选择裁剪位置，但在部分图片比例下存在以下问题：

- 图片可以被拖动到超出有效选框区域的位置；
- 拖动后可能出现裁剪范围与真实可见区域不一致；
- 预览端内部记录的偏移量与 CSS `object-position` 显示结果没有严格对应。

### 根因分析

Type E 预览端使用：

```css
object-fit: cover;
object-position: ...;
```

图片在正方形容器中显示时会先按 `object-fit: cover` 规则缩放：

- 纵向图片：宽度填满正方形，高度按比例放大并上下溢出；
- 横向图片：高度填满正方形，宽度按比例放大并左右溢出；
- 方形图片：无溢出，理论上不需要拖动。

修复前 `getMaxOffset()` 直接用原始图片像素和预览 CSS 像素计算：

```javascript
maxOffsetY = Math.max(0, (naturalHeight - displaySize) / 2);
maxOffsetX = Math.max(0, (naturalWidth - displaySize) / 2);
```

这里混用了两个不同坐标系：

- `naturalWidth` / `naturalHeight` 是原始图像像素；
- `displaySize` 是浏览器预览中的 CSS 像素。

因此计算出的最大拖动范围通常远大于实际有效范围，导致图片能被拖出选框或产生错误裁剪状态。

此外，修复前 `calculateObjectPosition()` 使用：

```javascript
return `${50 + (x / state.squareSize) * 100}% ${50 + (y / state.squareSize) * 100}%`;
```

这相当于把 `state.imageOffset` 当作 `object-position` 的百分比代理值，而不是实际渲染后的像素偏移；当 `getMaxOffset()` 改为真实渲染尺寸模型后，如果不同步修改 `calculateObjectPosition()`，仍会产生数学模型不一致。

### 修复方案

在 `src/renderer/js/styles/type-E-preview.js` 中建立统一的“预览像素偏移模型”。

#### 1. 新增通用数值钳制函数

```javascript
function clamp(value, min, max) {
  return Math.max(min, Math.min(max, value));
}
```

用于限制拖动偏移量和 `object-position` 百分比，避免超出有效范围。

#### 2. 新增 Type E 图片渲染指标计算函数

新增 `getRenderedImageMetrics()`，根据 `object-fit: cover` 后的实际渲染尺寸计算可拖动范围。

核心规则：

```javascript
if (isPortrait) {
  renderedHeight = displaySize * (naturalHeight / naturalWidth);
  maxOffsetY = Math.max(0, (renderedHeight - displaySize) / 2);
} else {
  renderedWidth = displaySize * (naturalWidth / naturalHeight);
  maxOffsetX = Math.max(0, (renderedWidth - displaySize) / 2);
}
```

这样 `maxOffsetX/Y` 始终处于预览 CSS 像素坐标系中，与 `state.imageOffset` 保持一致。

#### 3. 重写 `getMaxOffset()`

修复后 `getMaxOffset()` 不再直接使用原始图片尺寸计算，而是从 `getRenderedImageMetrics()` 获取当前有效范围：

```javascript
function getMaxOffset() {
  const { maxOffsetX, maxOffsetY } = getRenderedImageMetrics();
  return { maxOffsetX, maxOffsetY };
}
```

#### 4. 新增 `clampImageOffset()`

统一限制 `state.imageOffset`：

```javascript
function clampImageOffset(offset) {
  const { maxOffsetX, maxOffsetY } = getRenderedImageMetrics();

  return {
    x: clamp(offset.x || 0, -maxOffsetX, maxOffsetX),
    y: clamp(offset.y || 0, -maxOffsetY, maxOffsetY)
  };
}
```

#### 5. 重写 `calculateObjectPosition()`

修复后不再使用 `offset / squareSize`，而是将当前偏移映射到有效的 `0%~100%` 范围：

```javascript
const xPercent = maxOffsetX > 0 ? 50 + (x / maxOffsetX) * 50 : 50;
const yPercent = maxOffsetY > 0 ? 50 + (y / maxOffsetY) * 50 : 50;

return `${clamp(xPercent, 0, 100)}% ${clamp(yPercent, 0, 100)}%`;
```

映射关系：

| 偏移量 | object-position |
|--------|-----------------|
| `-maxOffset` | `0%` |
| `0` | `50%` |
| `+maxOffset` | `100%` |

这样可以确保 CSS 侧不会请求超出图片真实可裁剪范围的位置。

#### 6. 新增 `applyImageOffset()`

新增统一入口，先钳制偏移，再写入 DOM：

```javascript
function applyImageOffset() {
  state.imageOffset = clampImageOffset(state.imageOffset);
  if (state.img) {
    state.img.style.objectPosition = calculateObjectPosition();
  }
}
```

`onDrag()`、`updatePreview()`、`resetImageOffset()` 都改为通过该函数更新图片位置，避免状态和 DOM 显示不一致。

## 二、Type E 导出偏移方向修复

### 问题描述

Type E 中拖动图片后，导出图片的裁剪区域与预览不一致，表现为导出获取到的偏移方向与实际预览方向相反。

例如：

- 预览中拖动到图片上方区域；
- 导出后却显示图片下方区域；
- 或横向图片左右裁剪方向反转。

### 根因分析

预览端通过 CSS `object-position` 控制图片的可见区域。对实际绘制位置而言，CSS 中的偏移关系等价于：

```text
图片绘制位置 = 居中位置 - 偏移量
```

但导出端修复前使用：

```javascript
const drawOffsetX = baseOffsetX + imageOffset.x * squareSize;
const drawOffsetY = baseOffsetY + imageOffset.y * squareSize;
```

这导致导出 canvas 中图片绘制方向与预览端相反。

### 修复方案

在 `src/renderer/js/styles/type-E-export.js` 的 `renderImage()` 中，将绘制偏移符号从 `+` 改为 `-`：

```javascript
const drawOffsetX = baseOffsetX - imageOffset.x * squareSize;
const drawOffsetY = baseOffsetY - imageOffset.y * squareSize;
```

这样导出端与 CSS 预览端使用相同的偏移语义。

### 修改文件

| 文件 | 变更类型 | 说明 |
|------|----------|------|
| `src/renderer/js/styles/type-E-export.js` | 修改 | 修复 Type E 导出裁剪偏移方向 |

## 三、Type E 重选图片 EXIF 刷新修复

### 问题描述

Type E 样式中点击“重新选择”导入新图片后，编辑面板中的 EXIF 信息可能无法正确刷新为新图片信息。

涉及字段包括：

- 相机厂商 / Logo；
- 机型；
- 光圈；
- 快门；
- 焦距；
- ISO；
- 拍摄时间。

### 根因分析

本问题涉及 `src/renderer/js/app.js` 中图片加载和 EXIF 表单回填流程。

#### 1. Electron 路径中 EXIF 更新依赖图片 load 事件

修复前 `loadImageInElectron()` 的流程是：

```javascript
resetForm();
userImage.src = `file://${imagePath}`;
if (userImage.complete) {
  updateExifDisplay();
  updateBorder();
  applyDynamicBackground(userImage);
} else {
  userImage.addEventListener('load', () => {
    updateExifDisplay();
    updateBorder();
    applyDynamicBackground(userImage);
  }, { once: true });
}
```

但 `updateExifDisplay()` 只依赖 `currentExif` 和表单 DOM，不依赖图片像素是否加载完成。将它挂在图片 `load` 事件上会引入不必要的时序耦合，在缓存、快速重选、同一路径重选等情况下可能导致表单刷新时机异常。

#### 2. Electron 无 EXIF 时的文件修改时间回退会被清空

修复前无 EXIF 时会先写入文件修改时间：

```javascript
dateTime.value = ...;
```

随后又执行：

```javascript
resetForm();
```

导致回退时间被清空。

#### 3. 浏览器路径重选未等待异步 EXIF 读取

修复前浏览器路径重选回调为：

```javascript
input.onchange = (e) => { if (e.target.files[0]) loadImageWithExif(e.target.files[0]); };
```

`loadImageWithExif()` 是异步函数，但这里没有 `await`，快速连续重选时存在旧异步结果覆盖新图片信息的风险。

#### 4. 旧异步 EXIF 结果可能覆盖新图片

如果用户快速连续重选图片，较早一次的 EXIF 读取可能晚于较新一次返回，从而覆盖新图片对应的表单字段。

### 修复方案

#### 1. 增加图片加载序号

新增：

```javascript
let imageLoadSequence = 0;
```

每次进入图片加载流程时递增：

```javascript
const loadId = ++imageLoadSequence;
```

异步 EXIF 读取返回后检查：

```javascript
if (loadId !== imageLoadSequence) return false;
```

这样旧异步结果不会覆盖新选择图片的状态。

#### 2. 新增日期格式转换函数

新增 `formatDateTimeForInput(value)`，统一将 EXIF 日期或文件修改时间转换成 `<input type="datetime-local">` 需要的格式：

```text
YYYY-MM-DDTHH:mm
```

兼容格式包括：

- `YYYY:MM:DD HH:mm:ss`
- `YYYY:MM:DD HH:mm`
- `YYYY-MM-DD HH:mm:ss`
- `YYYY-MM-DD HH:mm`
- ISO-like 字符串
- 可被 `new Date()` 解析的字符串

#### 3. Electron 路径中将 EXIF 表单更新与图片 load 解耦

修复后流程调整为：

1. 读取并解析 EXIF；
2. 如果无 EXIF，读取文件修改时间到局部变量 `fallbackDateTimeValue`；
3. 确认当前加载序号仍有效；
4. `resetForm()` 清空旧表单；
5. Type E 下重置图片裁剪偏移；
6. 调用 `updateExifDisplay()` 填充 EXIF；
7. 如无 `DateTimeOriginal` 且存在 `fallbackDateTimeValue`，写回日期字段；
8. 设置 `userImage.src`；
9. 图片 `load` / `complete` 分支只负责 `updateBorder()` 和 `applyDynamicBackground()`。

#### 4. 浏览器路径重选增加 await

修复后：

```javascript
input.onchange = async (e) => {
  if (e.target.files[0]) await loadImageWithExif(e.target.files[0]);
};
```

#### 5. Type E 新图片加载时重置裁剪偏移

在 `loadImageWithExif()` 和 `loadImageInElectron()` 中，如果当前样式为 Type E，则调用：

```javascript
typeEPreview.resetImageOffset();
```

避免新图片沿用上一张图片的拖动偏移，导致预览和导出初始状态不一致。

## 六、影响范围说明

本次修改聚焦 Type E，但 `src/renderer/js/app.js` 是共享图片加载逻辑，因此需要关注跨样式影响。

### Type E 专属影响

- `type-E-preview.js` 中新增和修改的偏移函数只在 Type E 预览模块内部使用；
- `type-E-export.js` 中 `imageOffset` 仅由 Type E 导出路径使用；
- `exportImageHandler()` 仍只在 `currentStyle === 'type-e'` 时传递 `imageOffset` 和 `previewSquareSize`。

### 共享逻辑影响

`app.js` 中的图片加载流程会影响所有样式，但本次修改保持以下既有行为：

- Type B 的纵向图片校验逻辑保留；
- Type F / Type J 的机型字段仍保留 `Make + Model` 合并逻辑；
- 图片加载后的 `updateBorder()` 和 `applyDynamicBackground()` 仍在图片加载完成后执行；
- 浏览器路径与 Electron 路径都增加了异步防竞争机制，不改变用户交互入口。
